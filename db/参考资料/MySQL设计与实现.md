# MySQL 的设计与实现：从整体架构到核心机制

理解MySQL，不能只停留在索引、事务、锁这些独立知识点上。更重要的是理解：**MySQL如何把 SQL转化为高效的数据访问，如何组织磁盘数据，如何在并发访问和故障发生时保证事务的正确性。**

以下主要以 **MySQL 8.0 + InnoDB** 为分析对象。InnoDB 是 MySQL最主流的事务型存储引擎，下面会围绕它的设计展开，并区分 MySQL Server层和存储引擎层。

## 一、先建立整体架构模型

MySQL 可以理解为两个主要部分：

-   **Server 层**：负责连接、SQL 解析、优化、执行调度等数据库通用功能。
-   **存储引擎层**：负责数据如何存储、索引如何组织、事务如何实现、如何进行磁盘
    I/O 等。

``` text
客户端
  │ MySQL 协议
  ▼
MySQL Server 层
  ├── 连接管理：认证、会话、线程处理
  ├── SQL 解析：词法分析、语法分析、语义检查
  ├── 查询优化器：访问路径、连接顺序、成本估算
  └── 执行器：调用存储引擎接口、处理结果
  │
  ▼
InnoDB 存储引擎
  ├── 数据与索引：聚簇 B+ 树、二级索引
  ├── 内存管理：Buffer Pool、Change Buffer
  ├── 事务管理：MVCC、锁、Undo Log
  └── 持久化与恢复：Redo Log、刷盘、崩溃恢复
  │
  ▼
操作系统与存储设备
  文件系统、页缓存、SSD / HDD
```

### 1.1 为什么要分成 Server 层和存储引擎层？

这是一种职责分离设计。

Server
层不必关心记录最终以什么结构保存在磁盘上；存储引擎也不必重新实现完整的
SQL 解析和优化逻辑。

因此，MySQL 可以使用不同存储引擎，例如 InnoDB、MyISAM，而上层 SQL
接口基本保持一致。

但这种抽象不是完全隔离：优化器需要存储引擎提供索引、统计信息和访问成本估算；事务能力、锁行为等也取决于具体引擎。

### 1.2 从一条 SQL 看整个系统

假设执行：

``` sql
SELECT name
FROM user
WHERE id = 100;

UPDATE user
SET balance = balance - 100
WHERE id = 100;
```

查询大致经过：

1.  客户端建立连接并发送 SQL。
2.  Server 层完成解析、语义检查。
3.  优化器选择访问路径，例如使用主键索引。
4.  执行器调用 InnoDB 接口读取或修改记录。
5.  InnoDB 通过 Buffer Pool、B+ 树、事务和锁等机制完成操作。
6.  修改时生成 Undo Log 和 Redo Log，并按照事务提交与持久化规则处理。
7.  Server 层向客户端返回执行结果。

关键点：**SQL 执行、数据页修改、事务提交、磁盘持久化不是同一个动作。**
理解它们之间的关系，就能串起 MySQL 大部分核心机制。

## 二、SQL 执行引擎：一条 SQL 如何变成实际操作

### 2.1 连接与会话

客户端连接 MySQL 后，Server 层需要维护会话状态，例如：

-   当前用户及权限。
-   当前数据库。
-   事务状态和会话变量。
-   字符集、隔离级别、SQL 模式等。

连接处理模型和具体线程实现会随版本及配置变化。生产环境通常使用连接池，避免大量短连接反复建立和销毁的开销。

连接池并不等于数据库可以无限并发执行
SQL。连接过多会增加调度、内存、锁竞争和上下文管理成本。

### 2.2 SQL 解析

解析器主要完成两类工作：

-   词法分析：识别关键字、标识符、常量、运算符。
-   语法分析：根据 SQL 语法构建解析结构。

例如：

``` sql
SELECT name FROM user WHERE id = 100;
```

解析器识别出查询目标、数据表、过滤条件及常量。

随后还需要进行表、列、函数、权限等语义检查。解析成功不代表 SQL
一定能够执行，也不代表执行计划已经确定。

### 2.3 查询优化器

优化器解决的是：**在语义等价的执行方案中，选择预计成本较低的方案。**

例如：

``` sql
SELECT * FROM orders WHERE user_id = 100;
```

可能的执行方案包括：

-   全表扫描。
-   通过 `user_id` 二级索引定位记录。
-   先通过其他条件筛选，再回表。
-   与其他表连接时选择不同的连接顺序。

优化器会结合索引结构、数据分布统计信息、估算选择率、I/O 与 CPU
成本等因素做出决策。

索引存在，不代表一定会被使用。如果匹配记录比例很高，或者需要大量回表，全表扫描可能更便宜。

### 2.4 执行器与存储引擎接口

执行器按照执行计划推进操作，并调用存储引擎提供的接口。

可以粗略理解为：

``` text
执行器
  ├── 请求定位记录
  ├── 获取下一条记录
  ├── 检查过滤条件
  ├── 读取所需列
  └── 返回结果
```

这不是说每种执行计划都严格采用同一套流程，而是用来理解执行器与存储引擎的职责边界。

**本质上，Server
层负责决定和组织"做什么"，存储引擎负责具体实现"数据怎么读写"。**

## 三、存储结构：MySQL 如何组织磁盘上的数据

**InnoDB并不是把每条记录单独写成一个文件，而是以页为基本管理单位，通过索引组织页，再通过缓冲池管理内存中的页。**

整体可以分成四个层次：

  层次                主要职责
------------------- ---------------------------------------------------
  表空间 Tablespace   管理磁盘上的存储空间
  段 Segment          为索引树的不同部分组织页面空间
  区 Extent           组织一组连续页面，InnoDB 常规页大小下通常为 1 MiB
  页 Page             内存缓存、磁盘 I/O 和 B+ 树操作的基本单位

默认 InnoDB 页大小通常为 16
KiB，但可在初始化时配置。压缩表等特殊情况需要单独考虑。

### 3.1 为什么使用 Page，而不是直接读写一条记录？

假设一个订单记录只有 100 字节。

如果每次查询都直接针对一条记录发起磁盘 I/O，就会产生大量细碎的 I/O
请求。

数据库更适合以页为单位：

1.  读取包含目标记录的页。
2.  将整个页加载到 Buffer Pool。
3.  在内存中定位记录。
4.  修改记录后，将发生变化的页标记为脏页。
5.  后台或其他刷盘流程再将脏页写回存储设备。

这样，一次页读取可能让同一页中的多条记录受益。

代价是：即使只修改一条记录，InnoDB
管理的对象仍然是包含它的页，而不是一个独立的 100 字节文件。

### 3.2 表空间与文件

常见的 InnoDB 存储组织方式包括：

-   系统表空间：可承载多种系统级或共享存储内容。
-   独立表空间：每张表通常有自己的 `.ibd` 文件。
-   Undo 表空间：保存撤销记录。
-   Redo 日志文件：记录用于崩溃恢复的重做信息。

在常见的 `innodb_file_per_table=ON`
配置下，一张表的主要数据和索引存放在对应的独立表空间中。

但不能简单地认为"一个 `.ibd`
文件就只包含数据"：**表的聚簇索引、二级索引以及其他存储结构都可能占用这个表空间。**

### 3.3 页内部如何存放记录？

InnoDB 数据页通常包含：

-   页头：页类型、页号、状态等元数据。
-   Infimum / Supremum：页内记录组织所使用的边界记录。
-   用户记录：真正的数据行。
-   Page Directory：帮助在页内进行二分查找的目录槽。
-   页尾：校验等信息。

InnoDB 通过记录格式、记录头、链表关系和目录结构管理记录。

因此数据库查找一个记录通常分成两步：

1.  通过 B+ 树定位到目标数据页。
2.  在目标页内继续定位具体记录。

**B+ 树负责跨页定位，页内目录负责页内查找。**

## 四、索引的本质：为什么 InnoDB 选择 B+ 树

索引是数据库最重要的性能设计之一。InnoDB 的普通索引主要基于 B+ 树组织。

### 4.1 为什么不使用二叉搜索树？

假设有一亿条记录。

普通二叉搜索树可能严重倾斜，最坏情况下查找复杂度接近 `O(N)`。

平衡二叉树可以把高度控制在
`O(log N)`，但一个节点通常只能容纳少量键值，树高仍然较大。

数据库的瓶颈往往不是 CPU 比较次数，而是存储 I/O
次数。因此数据库希望每个节点尽可能容纳更多键值，减少树的高度。

### 4.2 B+ 树如何降低 I/O？

B+ 树具有几个重要特征：

-   内部节点保存分隔键和子节点指针。
-   叶子节点保存索引记录。
-   叶子节点按键值顺序组织，并通过链表支持范围扫描。
-   树通常保持平衡，所有叶子节点处于相同深度。

一个页可以存放大量索引项，所以树的分支因子很大。

假设每个内部节点平均有 500 个子节点，树高为 4 时，理论上可以覆盖约
`500^4`
个叶子节点位置。这个数字只是帮助理解数量级的简化模型，真实容量取决于索引项大小、填充率和页分裂等因素。

对于千万级、亿级数据，树通常只需几层。

因此，主键查询往往只需访问少数几个索引页。如果相关页面已在 Buffer Pool
中，就不需要每次都从存储设备读取。

### 4.3 为什么不是哈希索引？

哈希索引适合等值查找，例如：

``` sql
WHERE id = 100
```

但普通哈希结构不擅长：

``` sql
WHERE id BETWEEN 100 AND 200
ORDER BY id
```

B+ 树可以利用有序性支持：

-   等值查找。
-   范围查找。
-   排序与有序扫描。
-   前缀匹配等特定查询。

InnoDB
还存在自适应哈希索引机制，但它是基于热点访问模式建立的辅助结构，并不取代持久化的
B+ 树索引。

### 4.4 聚簇索引：InnoDB 最关键的索引设计

假设有如下表：

``` sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    age INT,
    balance DECIMAL(12, 2),
    KEY idx_age (age)
);
```

InnoDB 的聚簇索引叶子节点保存完整的行记录。

``` text
聚簇索引 PRIMARY KEY(id)
          │
          ▼
    根节点 / 中间节点
    键值范围与子页指针
          │
     ┌────┴────┐
     ▼         ▼
   叶子页 A   叶子页 B
   id=10      id=30
   完整行     完整行
   id=20      id=40
   完整行     完整行
```

所以：

``` sql
SELECT * FROM user WHERE id = 30;
```

通过主键索引定位到叶子记录后，就可以直接获得整行数据，不需要再查另一棵树。

如果表没有显式主键，InnoDB
会选择合适的唯一非空索引作为聚簇索引；如果也没有这样的索引，则会生成内部行
ID 作为聚簇索引键。

### 4.5 二级索引为什么需要回表？

二级索引 `idx_age(age)`
的叶子节点并不保存整行数据，而是保存索引键和对应的主键值。

例如：

``` text
二级索引 idx_age(age)
age=18 → id=20
age=25 → id=10
age=25 → id=40
```

执行：

``` sql
SELECT * FROM user WHERE age = 25;
```

典型过程是：

1.  在 `idx_age` 中找到符合条件的索引项。
2.  得到主键 `id=10`、`id=40`。
3.  根据主键分别查聚簇索引。
4.  读取完整记录。

这个过程称为**回表**。

如果查询只需要 `age` 和
`id`，这些字段已经包含在二级索引中，就可能直接通过二级索引返回结果，这叫覆盖索引。

``` sql
SELECT id, age
FROM user
WHERE age = 25;
```

覆盖索引减少了聚簇索引访问，通常可以显著降低 I/O。

### 4.6 为什么主键设计会影响全表性能？

因为每个二级索引叶子节点都需要携带主键值，所以主键越宽，所有二级索引通常也会越大。

主键设计会影响：

-   二级索引的空间占用。
-   Buffer Pool 的缓存效率。
-   插入时的页分裂和页面局部性。
-   范围查询和批量读取的效率。

因此，InnoDB
表通常适合使用简洁、稳定的主键。自增整数有利于顺序插入；随机 UUID
则可能导致更分散的插入位置和更高的页面维护成本。不过，最终选择仍然要考虑业务分布式
ID 需求、唯一性和写入模式。

参考：[InnoDB
索引结构与聚簇索引](https://dev.mysql.com/doc/refman/8.0/en/innodb-indexes.html)。

## 五、Buffer Pool：为什么 MySQL 的性能很大程度上取决于内存

如果每次 SQL 都直接读取磁盘，即使有 B+ 树，性能也会受到存储 I/O
延迟的限制。

InnoDB 使用 Buffer Pool 缓存数据页和索引页。

### 5.1 Buffer Pool 的工作方式

一次主键查询：

``` sql
SELECT * FROM user WHERE id = 100;
```

简化流程如下：

``` text
查询索引页
    │
    ▼
Buffer Pool 中是否存在？
    ├── 是：直接使用内存页
    └── 否：读取磁盘页 → 加载进 Buffer Pool
                               │
                               ▼
                          定位目标记录
```

Buffer Pool 缓存的是**页**，而不是简单的 SQL 结果集缓存。

因此，两条不同的 SQL 如果访问同一个数据页，也可以共享缓存收益。

### 5.2 LRU 与热点保护

InnoDB 使用 LRU
思路管理缓存，但并非简单地把最新读取的数据全部放在最前面。

它采用变体机制，包括新页进入列表的中间位置等策略，以减少一次大范围扫描将真正热点页全部挤出的风险。

除此之外，Buffer Pool 还涉及：

-   空闲页管理。
-   脏页管理。
-   页哈希查找。
-   多实例和并发访问管理。
-   后台刷新与淘汰。

### 5.3 什么是脏页？

当事务修改内存中的数据页时，Buffer Pool
中的页可能已经更新，而磁盘上的数据页仍然是旧版本。

此时，该页称为脏页。

``` text
磁盘数据页：旧值
     │
     │ 读取并加载
     ▼
Buffer Pool：旧值
     │
     │ UPDATE
     ▼
Buffer Pool：新值（脏页）
     │
     │ 后台刷盘
     ▼
磁盘数据页：新值
```

这就产生了一个关键问题：

**如果事务提交时数据页还没写回磁盘，服务器突然断电，如何保证已提交的数据不会丢失？**

答案不是要求每次提交都把所有修改过的数据页立即刷盘，而是引入 Redo
Log，并配合崩溃恢复机制。

## 六、Redo Log、Undo Log 与 Binlog：三种日志解决不同问题

这三者经常一起出现，但它们的目的不同。

  日志       所属层次       主要解决的问题
---------- -------------- ------------------------------------------
  Redo Log   InnoDB         崩溃后重做已记录的物理页修改，支持持久性
  Undo Log   InnoDB         回滚事务，并为 MVCC 提供旧版本数据
  Binlog     MySQL Server   记录逻辑变更事件，服务于复制、恢复等

不要把它们理解为同一种日志的不同名称。

### 6.1 Redo Log：为什么提交不需要立即刷数据页？

假设：

``` sql
UPDATE account
SET balance = 900
WHERE id = 1;
```

InnoDB 修改 Buffer Pool 中对应的数据页，并生成 Redo Log。

简化后的过程：

``` text
修改数据页
    ├── Buffer Pool 中的数据页变成脏页
    └── 生成 Redo Log
             │
             ▼
        写入 Redo Log Buffer
             │
             ▼
        按提交及刷盘策略持久化日志
             │
             ▼
        事务提交完成

稍后：后台将脏数据页刷回数据文件
```

核心思想是：**先保证恢复所需的日志按要求持久化，再允许数据页延后写入磁盘。**

这就是 Write-Ahead Logging（WAL，预写日志）的核心思想。

Redo Log
的生成、日志写入操作系统、日志真正持久化到存储介质，是不同阶段。它们是否同步以及何时完成，取决于配置和具体运行条件。

### 6.2 Redo Log 记录什么？

从设计原理上看，Redo Log
记录的是可用于恢复的页修改信息，而不是简单地保存一条完整 SQL。

例如：

``` sql
UPDATE account SET balance = 900 WHERE id = 1;
```

Redo Log 的重点不是再次执行这条 SQL，而是让 InnoDB
能够把相关数据页恢复到需要的状态。

这也解释了为什么 Redo Log 适合崩溃恢复：它不需要重新解析
SQL，也不依赖重新计算完整查询计划。

实际的日志记录格式、组织方式及恢复细节远比这个例子复杂，不能简单地将
Redo Log 理解成"把新值写进去"这一种操作。

### 6.3 Redo Log 为什么采用循环日志机制？

Redo Log 使用有限的日志空间循环复用。

``` text
日志空间：
┌─────────┬─────────┬─────────┬─────────┐
│ 已完成  │ 已完成  │ 新日志  │ 新日志  │
└─────────┴─────────┴─────────┴─────────┘
      ▲                         ▲
  可复用区域                 写入位置
```

这只是示意，不代表真实的日志文件布局。

关键概念有两个：

-   **LSN（Log Sequence Number）**：用于标识日志序列中的位置。
-   **Checkpoint**：表示恢复所需的日志边界推进到哪里，允许相应旧日志在满足条件后被复用。

脏页尚未安全刷盘时，某些相关日志仍然可能需要保留。因此，Redo Log
的复用速度会受到刷脏和 Checkpoint 推进能力的制约。

当日志产生速度长期超过系统能够推进 Checkpoint
的速度时，写入可能受到限制。这是分析高写入压力下 MySQL
性能的重要切入点。

### 6.4 Undo Log：回滚与历史版本

假设：

``` text
事务开始前：balance = 1000
事务修改后：balance = 900
```

如果事务回滚，数据库需要恢复原来的值。

Undo Log 保存重建旧版本或撤销修改所需的信息。

但 Undo Log 的用途不仅仅是回滚。它还支持
MVCC：当一个事务需要读取旧版本时，InnoDB
可以沿版本链构造符合该事务可见性规则的记录。

因此：

-   Redo Log 主要解决崩溃后的重做。
-   Undo Log 主要解决事务撤销和旧版本构造。

Undo Log
本身也涉及持久化和恢复规则，不能简单理解成"只存在内存中的备份"。

### 6.5 Binlog：为什么还需要 Server 层日志？

Redo Log 是 InnoDB 引擎自己的恢复日志；Binlog 则是 Server
层的二进制日志。

Binlog 常见用途包括：

-   主从复制。
-   基于时间点恢复。
-   配合备份恢复到指定时刻。
-   变更审计和数据同步。

两者的重要区别在于记录粒度与使用目的：

-   Redo Log 面向 InnoDB 内部的恢复。
-   Binlog 面向数据库逻辑变更的记录和传播。

Binlog 可采用 statement、row、mixed 等格式。生产环境中常见的 `ROW`
格式记录行级变更事件，而不是只记录原始 SQL 文本。

### 6.6 两阶段提交：如何协调 Redo Log 和 Binlog？

如果一个事务既修改 InnoDB 数据，又需要写入
Binlog，就必须防止两种日志的提交状态不一致。

简化流程：

1.  **Prepare**：InnoDB 写入事务的 Redo
    Log，并将事务标记为可提交的准备状态。
2.  **写入 Binlog**：Server 层将本事务对应的 Binlog 事件写入日志。
3.  **Commit**：通知 InnoDB 完成提交。

崩溃恢复时，MySQL 可以利用 Redo Log 的事务状态和 Binlog
中的事务记录协调判断，处理尚未完成的提交。

这里的"两阶段提交"是 MySQL 内部协调存储引擎与 Binlog
的机制，不应与分布式系统中协调多个独立参与者的通用两阶段提交协议完全等同。

### 6.7 持久性到底由什么保证？

在常见的高持久性配置下，重点关注：

``` ini
innodb_flush_log_at_trx_commit = 1
sync_binlog = 1
```

前者要求事务提交时按规定刷新并持久化 InnoDB Redo Log；后者要求 Binlog
按规定同步到存储设备。

但实际持久性仍然取决于操作系统、文件系统、存储控制器和设备是否正确兑现持久化请求。数据库配置正确并不等于任何硬件故障下都绝对不会丢失数据。

参考：[MySQL 的 ACID
模型](https://dev.mysql.com/doc/refman/8.0/en/mysql-acid.html)、[InnoDB
Redo
Log](https://dev.mysql.com/doc/refman/8.0/en/innodb-redo-log.html)。

## 七、事务系统：InnoDB 如何实现 ACID

事务系统的核心矛盾是：多个事务可以同时读写数据，但数据库又必须保证每个事务看到的数据符合规定，并且不能让并发操作破坏数据正确性。

InnoDB 采用的核心组合是：

-   Undo Log：维护旧版本。
-   MVCC：支持一致性读。
-   锁：控制冲突操作的并发。
-   Redo Log：支持崩溃恢复和持久性。
-   事务状态与提交机制：协调事务生命周期。

### 7.1 MVCC：为什么读操作通常不需要加锁？

假设账户余额最初为 1000。

``` text
当前版本：balance = 900
      │
      ▼
Undo Log 中的版本链
      │
      ▼
历史版本：balance = 1000
```

如果事务 T2 把余额从 1000 修改为 900，而另一个事务 T1
需要读取旧快照，那么 T1 不一定需要等待 T2 的数据页修改结束。

在符合 MVCC 可见性规则时，T1 可以利用 Undo Log 构造旧版本，读到 1000。

这就是多版本并发控制（MVCC）的核心思想：**读取历史上对当前事务可见的版本，而不必总是与写事务争抢同一把锁。**

### 7.2 InnoDB 如何找到历史版本？

InnoDB 记录中有用于多版本管理的隐藏信息，核心包括：

-   `DB_TRX_ID`：最近修改该记录的事务标识。
-   `DB_ROLL_PTR`：指向相关 Undo Log 记录的回滚指针。

当当前记录不符合某个读视图的可见性要求时，InnoDB 可以沿着版本链利用 Undo
Log 重建更早的记录。

版本链并不是无限保留的。历史版本在不再被活动读视图需要时，可以由 Purge
机制清理。

这也是为什么长期不结束的事务可能导致 Undo
历史堆积、清理延迟和存储压力增加。

### 7.3 Read View：哪个版本对事务可见？

Read View 可以理解为事务读取数据时使用的一组可见性判断信息。

它帮助判断：

-   某个事务是否已经提交。
-   某个版本的修改是否属于当前快照可见的范围。
-   是否需要沿版本链继续寻找旧版本。

在 MySQL 默认的 `REPEATABLE READ`
隔离级别下，普通一致性读通常以事务第一次建立的一致性读快照为基础，在该事务内重复读取时保持快照一致性。

在 `READ COMMITTED` 下，普通一致性读通常为每次读取建立新的快照。

这一区别决定了两个隔离级别在并发更新场景中的重要行为差异。

### 7.4 MVCC 不等于所有读操作都不加锁

``` sql
-- 普通一致性读
SELECT balance FROM account WHERE id = 1;

-- 锁定读
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
```

第一种通常走 MVCC 一致性读。

第二种则是锁定读，需要获取相应的锁，以便后续安全地修改数据。

因此，不能笼统地认为"SELECT
不加锁"。普通一致性读、锁定读和涉及特殊执行语义的查询需要分别分析。

## 八、锁机制：InnoDB 如何解决并发写冲突

MVCC 解决了大量读取场景的并发问题，但无法单独解决所有写冲突。

例如两个事务同时执行：

``` sql
UPDATE account
SET balance = balance - 100
WHERE id = 1;
```

如果二者都基于同一个旧值计算并覆盖写入，就可能造成更新丢失。因此，InnoDB
还需要锁机制协调冲突操作。

### 8.1 记录锁、间隙锁与 Next-Key Lock

  锁类型          主要作用
--------------- --------------------------------------
  Record Lock     锁定索引记录
  Gap Lock        锁定索引记录之间的间隙，限制特定插入
  Next-Key Lock   记录锁与对应间隙锁的组合

最重要的一点是：**InnoDB
的锁通常围绕索引记录和索引范围实现，而不是简单地对 SQL
中提到的逻辑行加锁。**

例如：

``` sql
SELECT *
FROM orders
WHERE user_id = 100
FOR UPDATE;
```

锁定哪些记录、是否涉及间隙，以及实际锁的范围，取决于索引结构、查询条件、隔离级别和执行计划等因素。

如果缺乏合适索引，数据库可能需要扫描更多记录，进而扩大锁竞争范围，甚至导致大量事务等待。

### 8.2 为什么会有间隙锁？

假设索引中存在：

``` text
10, 20, 30
```

事务 T1 执行一个范围锁定查询，希望保护某个索引范围。

如果只锁定已经存在的记录，那么另一个事务仍然可能插入一条新记录，例如
25。

这就可能破坏特定范围查询所需的并发语义。

间隙锁用于限制相应索引间隙中的插入，Next-Key Lock
则结合记录锁与间隙锁来实现相应的范围保护。

不过，间隙锁不是任何查询都一定会使用。实际锁定行为需要结合具体执行条件分析。

### 8.3 死锁是怎么产生的？

``` text
事务 T1：持有 A，等待 B
事务 T2：持有 B，等待 A
```

两者构成循环等待，无法继续执行。

InnoDB
可以检测死锁，并选择一个事务作为牺牲者进行回滚，使其他事务能够继续。

这意味着业务代码必须具备一定的事务重试能力。发生死锁不一定说明数据库存在缺陷，它也可能是高并发业务正常运行时暴露出来的锁顺序冲突。

常见的优化方式包括：

-   多个事务尽量按一致的顺序访问资源。
-   缩短事务持续时间。
-   为过滤条件建立合适索引。
-   避免在持锁期间进行不必要的网络调用。
-   对可安全重试的事务设计有限次数的重试与退避策略。

## 九、崩溃恢复：MySQL 宕机后如何恢复数据

假设一个事务已经提交，但对应的数据页还没有写入数据文件，MySQL 突然崩溃。

重启后，InnoDB
需要判断哪些已记录的修改应该恢复，以及哪些未完成事务需要撤销。

简化过程如下：

1.  **读取 Redo Log**：识别需要恢复的日志范围。
2.  **重做必要的页修改**：恢复日志所代表的已记录修改。
3.  **处理未完成事务**：通过事务状态和 Undo Log 撤销未提交修改。
4.  **恢复到可继续提供服务的状态**。

必须注意：Redo 恢复不等于"所有 Redo Log
都代表已提交事务"。崩溃时可能存在尚未完成提交的事务，因此恢复过程还需要识别事务状态并处理未提交修改。

### 9.1 Doublewrite Buffer 解决什么问题？

数据库以页为单位写数据，但如果发生突然断电，数据页写入可能只完成一部分，形成损坏的页，也就是常说的
torn page。

Doublewrite
机制通过额外的保护性写入，帮助数据库在数据页写入不完整时进行恢复。

它和 Redo Log 解决的问题不同：

-   Redo Log：重做需要恢复的修改。
-   Doublewrite：帮助保护数据页写入的完整性。

两者配合可以增强崩溃恢复能力。具体写入路径和实现细节取决于 MySQL
版本、操作系统及配置。

参考：[InnoDB Doublewrite
Buffer](https://dev.mysql.com/doc/refman/8.0/en/innodb-doublewrite-buffer.html)、[InnoDB
恢复](https://dev.mysql.com/doc/refman/8.0/en/innodb-recovery.html)。

## 十、复制与高可用：单机事务如何扩展到多节点

前面讨论的主要是单个 MySQL
实例内部的机制。生产环境通常还需要复制、故障切换和数据恢复。

### 10.1 主从复制的基本原理

典型的异步复制流程：

``` text
客户端
   │
   ▼
主库执行事务
   │
   ▼
写入 Binlog
   │
   ▼
从库接收并保存 Relay Log
   │
   ▼
从库应用事务变更
   │
   ▼
从库数据逐步追上主库
```

主从复制可以用于读扩展、数据冗余和故障切换。

但异步复制意味着：主库提交时，从库可能还没有应用该事务。如果主库立即故障，尚未传递或应用的事务可能造成数据丢失风险。

### 10.2 为什么主从复制不等于强一致性？

需要区分三个不同概念：

-   **复制**：将变更传递到其他节点。
-   **一致性读**：规定事务能够看到哪些版本的数据。
-   **高可用切换**：在节点故障时选择新节点继续服务。

这三个机制互相配合，但不能互相替代。

例如，应用把写请求发到主库，随后立即从异步从库读取，可能读到旧数据。

解决方案取决于业务要求，可以使用主库读取、会话级读写路由、等待复制进度或更强的复制与故障切换机制。

### 10.3 高可用系统还需要处理哪些问题？

生产级 MySQL 架构还必须考虑：

-   故障检测与主节点选举。
-   防止两个节点同时被当作主库接受写入。
-   复制延迟与数据丢失窗口。
-   故障切换后的连接重建和事务重试。
-   备份、恢复与数据校验。
-   在线 DDL、容量规划及故障演练。

单纯配置一个主库和一个从库，并不能自动构成完整的高可用系统。

## 十一、把整个 MySQL 设计归纳成一张图

``` text
SQL 层：决定如何执行
解析器 → 优化器 → 执行器
          │
          ▼
索引与存储层：决定如何找到数据
B+ 树 → 聚簇索引 / 二级索引 → 数据页
          │
          ▼
内存层：减少磁盘访问
Buffer Pool → 脏页 → 后台刷盘
          │
          ▼
事务层：保证并发正确性
MVCC + 锁 + Undo Log
          │
          ▼
持久化层：保证故障后的恢复能力
Redo Log + Binlog + Doublewrite + 恢复机制
```

这些设计不是孤立的。例如：

-   B+ 树降低查找成本，但需要 Buffer Pool 缓存热点页面。
-   Buffer Pool 允许延迟写数据页，但必须借助 Redo Log 保障恢复能力。
-   MVCC 减少读写冲突，但需要 Undo Log 保存可重建的历史版本。
-   二级索引加速查询，却增加存储占用和写入维护成本。
-   Binlog 支持复制与恢复，但需要与 InnoDB 的提交过程协调。

**MySQL
的本质，是围绕数据访问效率、并发正确性和故障恢复三大目标，构建的一套相互协作的存储与事务系统。**
