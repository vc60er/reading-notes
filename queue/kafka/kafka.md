2. 高吞吐如何实现
	1. **批量化：** Producer、Broker、Follower、Consumer 都可以按批次处理消息，减少每条消息承担的固定开销。
	2. **顺序日志与页缓存：** 以追加写为主，避免大量随机更新；借助操作系统页缓存提升读写效率。
	3. **高效网络传输：** 通过批量网络请求、减少数据拷贝，以及适用场景下的**零拷贝机制**降低传输开销。
	4. **Partition 并行化：** 不同 Partition 可以分布在不同 Broker 上并行处理，消费也可以按分区并行扩展。
	5. **统一日志格式与压缩：** 生产、存储、复制和消费尽量复用批次数据结构；压缩可以减少网络和磁盘带宽消耗。
	
	这些机制共同减少了单位消息消耗的 CPU、网络、磁盘 I/O 和内存带宽。不过，批次过大可能增加等待延迟和内存占用；压缩可能增加 CPU 开销；副本确认也会增加写入延迟。因此，吞吐量、延迟、可靠性需要结合实际业务进行权衡。

3. 高可靠是如何实现的
	> 通过数据冗余、同步状态管理和自动故障切换，避免单点故障导致服务不可用或已提交数据丢失。
	1. 存储安全：副本机制，解决数据冗余
		> 一个 Partition 保存多个副本，分布在不同 Broker 上。单个 Broker 故障时，仍有其他副本可用。
	2. 写入安全：副本同步完成确认，ISR + ACK：解决写入确认
		> Leader 等待 ISR 中的副本满足确认条件后，才向生产者返回成功；配合 min.insync.replicas，避免副本不足时仍然接受高风险写入。
	3. 故障自动切换：Leader 选举：解决故障恢复
		> Leader 故障后，从符合选举条件的副本中选出新 Leader，恢复读写服务。
	4. 读取安全：Offset 管理：解决消费进度
		> 记录消费者处理到哪里，避免故障恢复后跳过尚未成功处理的消息。


4. 不丢数据是如何实现的
	1. 生产端：足够副本确认后才报告成功。
		> 核心配置：acks=all + replication.factor=3 + min.insync.replicas=2。
		1. 先确保有足够的副本参与写入，再向生产者确认成功。
		2. 副本不足时宁可拒绝写入，也不降低写入安全性。
	2. 存储端：通过 ISR、HW 和安全选举降低故障丢数据风险
		1. ISR 机制： 跟踪与 Leader 保持足够同步的副本。
		2. HW（High Watermark）： 控制普通消费者可以读取的已提交日志范围。
		3. 安全的 Leader 选举： 避免选举落后副本造成已确认数据丢失。
		4. 故障域隔离： 将副本分散到不同机器、机架或可用区，降低同时故障的概率。
	3. 消费端：避免消息被跳过
		1. 避免丢失： 业务成功后再提交 Offset。
		2. 避免重复造成错误： 业务接口实现幂等，或使用去重机制。
		3. Kafka 内部消费后再生产： 可以使用 Kafka 事务实现原子性。
		4. 涉及外部数据库： 仍需考虑数据库事务、幂等或 Outbox 等方案
